### PIOA–PIOE — Parallel Input/Output Controllers
*   **Base Address:** `0x400E_0E00` (PIOA), then one port every `0x200`: PIOB `0x400E_1000`, PIOC `0x400E_1200`, PIOD `0x400E_1400`, PIOE `0x400E_1600`
*   **Why It's There:** Controls the chip's pins. Each pin is either handed to a peripheral such as the UART (pin muxing) or used directly as an input or output, for example to light an LED or read a button.
*   **The Problem:** Board initialisation code writes many PIO registers before anything else works, and often reads status registers back to check the result. Most settings come as three registers: one that sets bits, one that clears bits, and a read-only status register showing the result (for example `PIO_PER` `+0x00`, `PIO_PDR` `+0x04`, `PIO_PSR` `+0x08`). Plain store-and-readback gets these wrong, because the status would never change.
*   **Stub Logic:** Every set / clear / status group works as on the real chip. Output data can be set (`PIO_SODR`, `+0x30`), cleared (`PIO_CODR`, `+0x34`) or written directly (`PIO_ODSR`, `+0x38`, only on pins enabled through `PIO_OWER`). Pin levels (`PIO_PDSR`, offset `+0x3C`) read the driven value on output pins; other pins read what the outside world drives, which is 1 (as if pulled up with nothing pressing them) unless the emulator's `--pin=` option changes it. The peripheral select registers (`PIO_ABCDSR`, `+0x70` and `+0x74`) and the other configuration registers are store-and-readback. **Interrupts:** a change on a pin sets its bit in `PIO_ISR` (`+0x4C`), which reading clears. The port asks for its interrupt (IRQ 10, 11, 12, 16, 17 for PIOA to PIOE) while a bit set in `PIO_ISR` is also enabled in `PIO_IMR` (`+0x48`, through `PIO_IER` / `PIO_IDR`). By default both edges count; a pin enabled in `PIO_AIMMR` (`+0xB8`) uses `PIO_ELSR` (`+0xC8`) to choose edge or level and `PIO_FRLHSR` (`+0xD8`) to choose rising/high or falling/low. The glitch filter and debouncing are not modelled. Every register starts at 0; the real per-port reset values are not modelled.
